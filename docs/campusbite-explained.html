Chapter 1

The big picture

CampusBite is a pre-order app for campus canteens. A student opens it on their phone, picks an outlet (Main Food Court, Juice Junction or Night Canteen), adds dishes to a cart, picks a 15-minute pickup slot and pays from a prepaid wallet. They get a token number and a QR code. The outlet sees the order on a live board, cooks it, marks it ready, and scans the student's QR at the counter to hand the food over.

There are three kinds of users:

  • Student: browses, orders, pays, tracks, rates dishes.
  • Vendor (outlet owner): accepts and cooks orders, verifies pickups, edits menu, stock and prices, reads sales reports.
  • Admin: sees every outlet and every user.
The single most important design decision: all the business rules live inside the Oracle database, in PL/SQL. The web server is only a messenger. That is what makes this a DBMS project instead of a web project with a database bolted on.
Chapter 2

The three layers

Think of a restaurant. The menu card you hold is the front-end. The waiter who carries your order to the kitchen and brings back the plate is the server. The kitchen, with its recipes, its stock room and its rules ("we don't serve biryani after it runs out") is the database.
Layer 1 · Front-end

What you see

HTML, CSS and JavaScript running in the phone's browser (public/). It draws screens and sends requests. It never talks to Oracle directly.

Layer 2 · Server

The messenger

A Node.js program using Express (server/). It receives requests like "place this order", checks who is logged in, and calls the right PL/SQL procedure.

Layer 3 · Database

The brain

Oracle 21c with 15 tables, the canteen_pkg package and 9 triggers (db/). It stores everything and enforces every rule.

Chapter 3

One order, start to finish

Follow Siddharth ordering 2 Maggi and 1 Chicken Roll from Night Canteen with the coupon EXAM10. Every numbered step names the exact piece of code doing the work.

Part A · Placing the order

  1. Browsing. The outlet page calls GET /api/outlets/3/menu. The server runs a SELECT on the view v_menu and sends back dishes with prices, stock and photos.
  2. The cart. Tapping ADD only changes the cart stored in the browser (localStorage). Nothing reaches the database yet.
  3. Choosing a slot. Checkout calls GET /api/outlets/3/slots, which runs SELECT * FROM TABLE(canteen_pkg.get_slots(3, 16)). That function works out the next 15-minute slots and how many places each has left.
  4. Pay. The browser sends POST /api/orders with the outlet, the cart as JSON ([{"item_id":21,"qty":2},{"item_id":25,"qty":1}]), the coupon and the slot.
  5. The server calls the procedure. server/routes/student.js runs BEGIN canteen_pkg.place_order(...); END;, passing the logged-in user's id from the session. It never trusts a user id sent by the browser.
  6. Inside place_order (file db/03_package.sql):
    • Sets a savepoint, a bookmark to rewind to if anything fails.
    • Locks the student's row (SELECT ... FOR UPDATE) so two payments can't spend the same money at once.
    • Checks the outlet isn't paused and the slot is valid: on the 15-minute grid, in the future, inside opening hours.
    • INSERT INTO orders. Two triggers fire automatically:
      • trg_order_token gives today's next token number and a secret 6-digit pickup code.
      • trg_order_slot books a place in the slot, or stops everything with "slot is full".
      The audit trigger also writes "PLACED" into order_status_log.
    • Opens a cursor over the JSON cart and, line by line, does INSERT INTO order_item. Each insert fires trg_order_item_stock, which:
      • copies the real price from the menu, so the browser cannot fake prices;
      • checks the dish belongs to this outlet, is available and has enough stock;
      • reduces the stock.
      If the stock drops low, trg_menu_stock_watch raises an alert or hides the dish.
    • Adds up the subtotal, calls the function calc_coupon_discount('EXAM10', subtotal), adds 5% GST and updates the order's totals.
    • Takes the money from the wallet (UPDATE app_user SET wallet_balance = wallet_balance - total). trg_wallet_guard stops it with a clear message if the balance would go negative. A DEBIT row is written to the wallet ledger.
    • COMMIT: everything becomes permanent together. If any step failed, ROLLBACK TO the savepoint undoes all of it: no half order, no lost stock, no money taken.
  7. The answer comes back. The procedure's OUT parameters (order id, token, total) go back to the server, which replies with JSON. The browser opens the order page and draws the QR code from CAMPUSBITE:<order id>:<pickup code>.

Part B · Cooking and pickup

  1. The vendor's board refreshes every 5 seconds (GET /api/vendor/orders) and beeps when a new order appears.
  2. Accept, Start cooking, Mark ready: each click calls canteen_pkg.update_order_status. The function is_valid_transition blocks illegal jumps such as PLACED straight to READY. Every change is logged by the audit trigger.
  3. The student's order page also refreshes every 5 seconds. When it sees READY, the phone beeps and vibrates.
  4. At the counter the vendor taps Scan pickup QR. The camera reads the code and the server calls canteen_pkg.verify_pickup. It checks the order belongs to this outlet, the code matches, the order is READY and hasn't been collected already. Only then does it set PICKED_UP.
  5. That status change fires trg_loyalty_points: 1 point for every ₹10 spent. The student can now rate each dish, and trg_review_rating updates the dish's average rating.

Constraints: the rules on the columns

Constraints are rules Oracle checks on every insert and update. If a rule is broken, the change is refused.

ConstraintPlain meaningExample here
PRIMARY KEYThe unique ID of each row. No duplicates, never empty.order_id in orders; (order_id, item_id) together in order_item
FOREIGN KEYA column must point to a row that really exists in another table.An order's user_id must exist in app_user; an order's (outlet_id, pickup_slot) must exist in pickup_slot
UNIQUENo two rows can share this value.Email, registration number, dish name within one outlet
CHECKA yes/no condition the value must pass.Price > 0; wallet ≥ 0; rating 1–5; status in a fixed list; phone is 10 digits; booked ≤ capacity on slots
NOT NULLThe field cannot be left empty.Names, prices, emails
DEFAULTValue used when none is given.New users get role STUDENT and wallet 0
IDENTITYOracle numbers new rows automatically (1, 2, 3 and so on).user_id, order_id, item_id
ON DELETE CASCADEDeleting a parent deletes its children too.Delete an order and its order_item rows go with it

Views are saved queries that behave like read-only tables. v_menu joins dishes with their outlet and category names. v_order_details joins orders with the customer and outlet, and builds the "Maggi Masala x2, Chicken Roll x1" text with LISTAGG. The server reads these views, so the joins are written once, in the database.

Indexes work like the index at the back of a book. They let Oracle find, for example, "all orders of outlet 3 with status PLACED" without reading every row.

Chapter 5

Normalization, 1NF to BCNF

Normalization means splitting data into tables so that each fact is stored in exactly one place. Then you can't update a fact in one place and forget another copy. Here is how the schema meets each level, using a single "everything in one sheet" table as the starting point.

Unnormalized start: one row per order, holding Order 64, Siddharth, 24BCI0158, Night Canteen, Men's Hostel Block C, "Maggi x2, Chicken Roll x1", ₹40, ₹90...

1NF: one value per cell

A cell like "Maggi x2, Chicken Roll x1" holds several values, so the dishes move to their own rows: order_item(order_id, item_id, qty, unit_price), one row per dish. That text appears only when the view builds it for display; it is never stored.

2NF: no partial dependency

In order_item the key is the pair (order_id, item_id). qty depends on the whole pair. But a dish's name depends only on item_id, which is half the key, so names live in menu_item and not in order_item. Likewise the customer's name depends only on the order, and the order only stores user_id.

3NF: no transitive dependency

A dish row could store "outlet location", but location depends on the outlet, not on the dish (dish → outlet → location). So menu_item keeps only outlet_id, and the location lives in outlet. The same goes for category names (category table) and the order's customer details (app_user).

BCNF

In every table, whatever decides the other columns is a key: email and reg_no in app_user are UNIQUE (candidate keys), as is (outlet_id, name) in menu_item. No non-key column decides another.

Deliberate, controlled copies you should be ready to explain:
  • order_item.unit_price is a snapshot of the price at order time. When a vendor changes a price tomorrow, yesterday's bill must not change. That makes it a separate fact, not a duplicate.
  • menu_item.rating_avg, app_user.wallet_balance and pickup_slot.booked could be recalculated from other tables. They are stored for speed, and triggers or procedures keep them correct automatically. This is called controlled denormalization.

Package rubric: 7 marks

A package is a folder that groups related functions and procedures under one name: canteen_pkg. It has two parts:

  • Specification (the "menu card"): the list of what the outside world may call, plus shared constants such as c_gst_rate = 0.05 and c_max_topup = 5000.
  • Body (the "kitchen"): the actual code. It also contains private helpers that aren't in the specification, so nobody outside can call them: get_user, can_manage and do_cancel.

Why it matters: the GST rate is defined once; the server only needs one name to call everything; and hiding do_cancel means nobody can refund an order without going through the permission checks in cancel_order.

CREATE OR REPLACE PACKAGE canteen_pkg AS
  c_gst_rate CONSTANT NUMBER := 0.05;
  FUNCTION calc_coupon_discount (p_code VARCHAR2, p_subtotal NUMBER) RETURN NUMBER;
  PROCEDURE place_order (...);
  ...
END canteen_pkg;

A trigger is code that runs by itself when something happens to a table: before or after an INSERT, UPDATE or DELETE. Nobody calls it. Think of a motion-sensor light. :NEW means the row as it will be after the change, and :OLD the row as it was before.

Why triggers rather than application code: the rule holds no matter who changes the data. Even if someone types an UPDATE menu_item SET stock_qty = 0 by hand in SQL*Plus, the dish still hides itself.

CREATE OR REPLACE TRIGGER trg_menu_stock_watch
BEFORE UPDATE OF stock_qty ON menu_item
FOR EACH ROW
BEGIN
  IF :NEW.stock_qty = 0 THEN
    :NEW.is_available := 'N';                 -- sold out: hide it
  ELSIF :OLD.stock_qty = 0 AND :NEW.stock_qty > 0 THEN
    :NEW.is_available := 'Y';                 -- restocked: show it again
  END IF;
  ...
END;

Chapter 7

Extra Oracle features (beyond the syllabus)

  • Pipelined table function (get_slots): a function that returns rows one by one, so you can query it like a table: SELECT * FROM TABLE(canteen_pkg.get_slots(1, 8)). It needs two object types, t_slot_row (one row) and t_slot_tab (a list of them).
  • JSON_TABLE: turns the cart JSON text into rows and columns, so a cursor can loop over it.
  • MERGE ("update if it exists, insert if not"): used for the daily token counter, slot rows and daily summaries.
  • Compound trigger: one trigger with separate BEFORE and AFTER sections (the status audit).
  • Analytic (window) functions: ROW_NUMBER() OVER (...) renumbers tokens in the seed data; COUNT(*) OVER (...) builds "Order again".
  • LISTAGG: joins dish names into one display string in v_order_details.
  • Why token_counter is its own table: a row trigger on ORDERS can't safely read ORDERS to find "the highest token today" (the mutating table problem, and two orders at once could get the same token). A separate counter row, updated with MERGE, solves both.
Chapter 8

Transactions and safety

A transaction is a group of changes that succeed or fail together. These are the ACID properties in practice:

  • Atomicity: place_order starts with SAVEPOINT sp_place_order. If any check fails (out of stock, slot full, not enough money), ROLLBACK TO sp_place_order undoes everything. Test TC04 proves the stock and order count are unchanged after a failed payment.
  • Consistency: the CHECK, foreign key and unique constraints plus the triggers mean the data can never reach an impossible state (negative wallet, overbooked slot, review of an uneaten dish).
  • Isolation: SELECT ... FOR UPDATE locks the student's row and the dish row while an order is being placed, so two phones paying at the same moment wait in line instead of both spending the same ₹100. The slot's CHECK (booked <= capacity) stops overbooking even under a rush.
  • Durability: after COMMIT, Oracle guarantees the order survives a crash.

Security basics

  • Passwords are never stored. Only a salted scrypt hash is kept (server/auth.js).
  • Bind variables (:user_id, :outlet_id) send values separately from the SQL text, which blocks SQL injection.
  • The server takes the user's identity from the signed login cookie, never from the request body.
  • The pickup code is hidden from vendors in the API, so they must scan the student's QR to hand food over.
  • Prices always come from the menu table, never from the browser.
Chapter 9

How the front-end is connected

The browser side (public/)

  • Single-page app: one HTML page. JavaScript redraws the content when the address changes after the # (#/outlet/3, #/cart, #/order/64, #/v/board). This is called hash routing.
  • Talking to the server: a small helper api() uses the browser's fetch() to send and receive JSON.
  • Live updates: the order page and vendor board ask again every 5 seconds (polling).
  • QR: the qrcodejs library draws the student's QR; html5-qrcode uses the vendor's camera to read it (needs HTTPS).
  • Installable app (PWA): manifest.webmanifest and the service worker sw.js let phones "Add to Home screen" and open it like an app.

The server side (server/)

  • Express maps each URL to a handler. routes/student.js covers login, menus, slots, orders and the wallet. routes/vendor.js covers the order board, pickup, menu editing and reports.
  • node-oracledb (thin mode, so no Oracle client install is needed) keeps a connection pool: a few open database connections that requests share, instead of opening a new one every time.
  • db.js has helpers: query() for SELECTs, plsql() to call procedures and read OUT values and REF CURSORs, and toHttpError(), which turns ORA-20xxx errors into the readable message shown in the red pop-up.
  • Login is a signed cookie (cookie-session), so it also works when hosted on Vercel's serverless functions.

Chapter 10

Testing

db/05_tests.sql is one PL/SQL block that creates its own test outlet, vendor and students, runs 53 checks, prints a table of Expected / Actual / PASS or FAIL, and then deletes its test data. The demo data is never touched.

  • Happy paths: top-up, a correct total with GST, token assigned, stock reduced, wallet debited, ledger row written, loyalty points credited, rating updated.
  • Rules that must refuse: negative top-up, empty wallet, more than stock, sold-out dish, a dish from another outlet, expired coupon, PLACED → READY jump, wrong vendor, wrong pickup code, a reused QR, full slot, off-grid time, closed outlet.
  • Rollback proof: after a failed order, the order count and stock are exactly the same as before.

Run it with .\db\run.ps1 05_tests.sql. A screenshot of its output goes into the report's Verification & Testing section, alongside screenshots of the app.

Chapter 12

Questions you may be asked

Why put the logic in PL/SQL instead of JavaScript?

The rules then hold for every way the data can be changed: the app, SQL*Plus, or a future mobile app. It also keeps the checks and the data change in one transaction, close to the data, with fewer round trips.

Difference between a function and a procedure?

A function must return exactly one value and can be used inside SQL (SELECT calc_coupon_discount(...) FROM dual). A procedure performs actions and returns results through OUT parameters; it is called as a statement.

What is a mutating table error and how did you avoid it?

A row-level trigger can't query the table it is firing on in most cases. Token numbers would need "max token today from ORDERS" inside an ORDERS trigger, so a separate token_counter table is updated with MERGE instead.

BEFORE vs AFTER triggers?

BEFORE can still change the row being saved (for example :NEW.is_available := 'N', or setting the unit price). AFTER runs once the row is saved and is used to write to other tables (price history, loyalty points, ratings).

Explicit vs implicit cursor vs REF CURSOR?

Implicit: Oracle makes one for every single SQL statement (SQL%ROWCOUNT). Explicit: you declare, open, fetch and close it yourself (the cart loop). REF CURSOR: a pointer to a result set that can be passed out of a procedure to the application (the report procedures).

How do you stop two students booking the last place in a slot?

The booking is one UPDATE with WHERE booked < capacity, which also locks the slot row, and a CHECK constraint booked <= capacity as a final safety net. The second student gets ORA-20013 "slot is full".

What happens if payment fails halfway?

The whole order is rolled back to the savepoint: no order row, no order lines, stock restored, slot place released, no wallet change. Test TC04 checks this.

Is the schema in 3NF? Any exceptions?

Yes. The exceptions are deliberate: unit_price is a historical snapshot, and the cached totals (rating_avg, wallet_balance, booked) are kept correct by triggers and procedures. That is controlled denormalization, done for speed.

How does the front-end talk to Oracle?

It doesn't, directly. The browser calls REST endpoints on the Node.js server using fetch and JSON; the server uses node-oracledb with a connection pool and bind variables to call the package.

Why can't a vendor just mark an order as picked up?

update_order_status refuses PICKED_UP with ORA-20012. Only verify_pickup can set it, and only with the secret code that sits on the student's phone. So food can't be handed to the wrong person.
